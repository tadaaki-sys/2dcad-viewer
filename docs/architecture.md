# フォルダの役割と依存の向き

2D CAD Viewer を本格的な 2D CAD へ段階的に広げるための、フォルダの役割と規則です(Phase 1c で整理)。
規則は自動テスト `src/architecture.test.ts` で確認しています。違反すると `npm test` が失敗します。

## 全体の形

```
画面(React)  App.tsx / components/ / cad-view/
     │
     ▼
app/  アプリの動き(コマンドなど。画面の機能は使わない)
     │
     ▼
io/  ファイル形式の読み書き(DXF・DWG、ワーカーの中の処理)
     │
     ▼
core/  CADの中核(モデル・幾何・選択・スナップ・測定・表示の座標)
     │
     ▼
types/  共通の型(CadEntity など)
```

- **矢印の向き(上から下)にだけ、読み込んでよい**のが原則です。下の層は、上の層を知りません。
- **下の層へは、1つ飛ばしでも直接読み込んでよい**です。たとえば、画面から `core/` を直接使ってかまいません(`CadCanvas` は、選択やスナップを直接使っています)。

## 各フォルダの役割

| フォルダ | 役割 | 読み込んでよいもの | 使ってよい実行環境の機能 |
|---|---|---|---|
| `src/core/` | CAD の中核。画面にも、ファイル形式にも依存しない。 | `core/`、`types/` だけ。外部パッケージは使わない。 | ECMAScript の標準だけ(ブラウザの `window`・`document`・Canvas も、Node の機能も使わない) |
| `src/io/` | ファイル形式の読み書き。DXF・DWG の解析、元データの保持、**ワーカーの中で動く処理**。 | `io/`、`core/`、`types/`、決めたパッケージ(`dxf-parser`、`@mlightcad/libredwg-web`)。画面は読み込まない。 | ECMAScript の標準と、ワーカーで使える機能(`TextDecoder`、`WebAssembly`、`console` など)。DOM(画面)は使わない。 |
| `src/app/` | アプリの動き。コマンド(名前・別名・段階・依頼)など、画面と中核の間で「何をするか」を決める。React や画面の機能は使わない(だから単体テストできる)。 | `app/`、`core/`、`types/` だけ。外部パッケージは使わない。(`io/` は、保存とつなぐ段階で必要になったら、規則の変更として加える) | ECMAScript の標準だけ |
| `src/types/` | 共通の型。**型の宣言だけ**を置く(値・関数・クラスは置かない)。 | `types/` の型だけ(`import type`)。 | － |
| `src/cad-view/`、`src/components/`、`App.tsx`、`src/hooks/`、`src/utils/`、`src/devHooks.ts` | 画面(React と Canvas の描画)。**ワーカーを起動・管理するのも画面の側**(`App.tsx`)。 | すべて。ほかの層からは読み込まれない。 | すべて |

### 例外

- **DWG 変換の WASM:** `io/` は、`node_modules/@mlightcad/libredwg-web/wasm/` のフォルダだけを、相対パスで読み込んでよいです。パッケージが、このファイルを公開範囲(`exports`)に含めていないためです。`node_modules` のほかの場所を相対パスで読み込むことはできません。

### 規則の対象外(テスト用のもの)

次のものは、規則の検査の対象外です(何を読み込んでもよい)。その代わり、**本番のコードから、これらを読み込むことはできません。**

- テスト本体(`*.test.ts`、`*.test.tsx`)
- テスト用の補助(`testHelpers.ts`)
- 回帰テスト(`src/regression/`)、E2E(`e2e/`)

## 検査の方法

文字の検索ではなく、TypeScript 自身を使って検査します。そのため、コメント、文字列、変数名(`document` という名前のCADドキュメントなど)に惑わされません。

- **依存の向き:** 構文解析で、`import`、`export … from`、動的 `import()`、型の `import("…")`、`new URL("…", import.meta.url)` を取り出して調べます。読み込む先を文字列で直接書いていない動的 `import()` は、違反とします。
- **実行環境の機能:** `core/` と `types/` は「ECMAScript の標準の型だけ」で、`io/` は「ECMAScript とワーカーの型だけ」で、型チェックします。使ってはいけない機能(`window`、`document.createElement`、`localStorage`、Canvas など)を使うと、TypeScript が「見つからない」として検出します。

### 変更の内容(`ChangeSet`)の約束事(Phase 3)

- 変更は、**必ず `ChangeSet` として** `DocumentSession.apply()` を通す。図面(`CadDocument`)を直接書き換えない。
- 位置(`index`)は、その変更を適用する直前の、描画順の配列での位置。1つの `ChangeSet` の中の変更は、書かれた順に適用する。
- 削除・置き換えは、その位置にある図形が「同じオブジェクト」であることを確かめる。一致しなければ、何も変えずに失敗する(図面が履歴と食い違ったまま進むことを防ぐ)。
- 新しい図形のID(`n<番号>`)は、`DocumentSession.allocateEntityId()` で払い出す。Undo しても払い出し番号は戻らず、同じIDを別の図形に使い回さない。
- コマンドは `addEntitiesChangeSet`・`removeEntitiesChangeSet`・`replaceEntitiesChangeSet` で変更を作る(位置の計算を間違えないため)。
- 描画順の入れ替え(`move`)は、「from の位置の図形を取り出して、取り出したあとの配列の to の位置に入れる」。最前面・最背面への移動は `moveToFrontChangeSet`・`moveToBackChangeSet` で作る(指定した図形どうしの前後関係は保つ)。
- **保存の Phase への申し送り:**
  - 新しく描いた図形は、DXF の ENTITIES 区画に記録として挿入する。描画順の入れ替えは、記録の位置の入れ替え(取り出して、挿入)として扱う。いまの差分の適用(`io/dxf/patch.ts`)は、置き換えと削除だけなので、挿入を足す必要がある。
  - 新しい図形の色は、レイヤー色を数値にして持っている(取り込んだ図形と同じ扱い)。保存では、レイヤー色の指定(BYLAYER)に戻す。
- **編集系のコマンド(Phase 4以降)の約束:** 展開済みのブロックの図形や、寸法など「読み取り専用」の図形は、編集しない。判断に使う分類(editable / readOnly)は `io/` にあるので、`app/` の層が受け取ってコマンドに渡す(`core/` は `io/` を読み込めないため)。

## `app/` の中身

| フォルダ | 内容 |
|---|---|
| `app/commands/` | アプリに最初から入っているコマンド(OPEN・CLOSE・FIT・MEASURE・FULLSCREEN・UNDO・REDO・LINE・PLINE・RECT・CIRCLE・ARC・TOFRONT・TOBACK・OSNAP・SNAP・GRID・ORTHO・POLAR・OTRACK・ID)。コマンドが返す「アプリへの依頼」(`AppRequest`)の型と、コマンドを始める時点の状態(`AppCommandContext`: 図面が開いているか、描く先、ID の払い出し)。依頼を実際に実行するのは画面の側(`App.tsx`)。 |
| `app/document/` | `DocumentSession`(開いている図面のドキュメントと変更の履歴を持ち、変更を購読者に知らせる。未保存の判定 `isDirty` と `markSaved()` を持つ)、元に戻す結果のメッセージ、ドキュメントから描画用モデルを作る処理、選択中の図形の描画順の変更(`reorderSelection`)。 |
| `app/drawing/` | 作図の部品。新しい図形(線・ポリライン・長方形・円・円弧)を作る処理と、描く先(現在のレイヤー)の決定。 |

### 作図(Phase 4)の約束事

- 作図コマンドは、図面を直接変更せず、「図形を追加する」依頼(`addEntities`)を返す。画面の側が `DocumentSession.apply()` を通して適用する。**1つのコマンドで描いた分は、1つの Undo の単位**になる。
- 点を順に指示するコマンド(LINE・PLINE)は、Enter(空)と Esc のどちらでも終了し、描いた分を確定する(`onCancel`)。`U` で1点戻す、`C` で閉じる(3点以上)。作図中の Ctrl+Z は `U` として働く。
- ゴム紐(描いている途中の仮の図形)は、コマンドの段階が返す形式に依存しない折れ線(`PreviewShape`)を、画面が重ねて描くだけ。図面のデータは変えない。
- 描く先は「現在のレイヤー」(レイヤー欄で選ぶ。初期値はレイヤー `0`)。非表示のレイヤーには描かない。新しい図形の色は、そのレイヤーの色。
- 描画順: 新しい図形は常に最前面(末尾)に追加する。`TOFRONT`・`TOBACK` は、この作業で新しく描いた図形(ID が `n<番号>`)だけが対象。取り込んだ図形の順序変更は、編集してよい図形かの分類(io の editable / readOnly)をアプリの層へ渡す仕組みと一緒に、Phase 9 で行う。
- 未保存の保護: 変更があると「未保存の変更あり」と表示し、図面を閉じる・別の図面を開く・ページを閉じる(再読み込み)ときに確認を出す。
  - 確認は、画面の状態ではなく `DocumentSession.isDirty` を直接読んで判断する(作図の途中で「閉じる」を押すと、描きかけの図形を確定してから閉じる依頼が続くため、画面の状態はまだ古い)。
  - 描きかけで、まだドキュメントに入っていない図形(LINE・PLINE で2点以上)も、ページを閉じる前の確認の対象にする(`ActiveCommand.hasPendingChanges`)。
  - 新しい図面を読み込んでいる間は、いまの図面を変更しない(作図コマンドは始まらず、元に戻す・やり直し・描画順は拒否する)。読み込みが終わると、いまの図面と変更は置き換えられるため。
  - 保存の Phase では、保存を始める時点で `saveToken` を控え、成功したら `markSaved(token)` を呼ぶ(保存している間に編集が進んでも、保存できた状態だけを保存済みにするため)。`markSaved` と、履歴の破棄(`reset`)は、購読者に状態の変化を知らせる。

### 円・円弧(Phase 5)の約束事

- **角度の規約:** ラジアン。+X軸から反時計回り(CCW)。ワールドのY軸は上向き。保存する円弧は、常に「始点から終点へ反時計回り」で表す(DXFの ARC と同じ)。角度は `[0, 2π)` にそろえる(`core/geometry/construct.ts`)。
- **CIRCLE:** 中心 → 半径。半径は、点の指示(中心からの距離)か、数値の入力。`D` で、直径の数値入力(半径はその半分)。点を待つ段階が数値だけの入力を受け取るには、段階に `acceptsDistance: true` を宣言する(宣言しない段階では、これまでどおりエラー)。
- **ARC:** 標準は3点(始点 → 通過点 → 終点)。3点が通る向きから、反時計回りの始点・終点に直す(時計回りに指示したら、始点と終点を入れ替える)。`C` で、中心 → 始点(半径が決まる)→ 終点(中心からの方向だけを使う。反時計回り)。
- **作らない円・円弧:** 半径が `MIN_RADIUS`(1e-6)未満か `MAX_RADIUS`(1e9)超、3点が一直線(2辺の間の角の sin が 1e-9 以下)や同じ点を含む、中心・始点・終点で、終点が中心と同じ点・始点と同じ方向(角度の範囲が `1e-9` ラジアン未満、または全周との差が同じ未満)、座標が有限でない点を含む。3点が通る円は、中心を絶対座標へ戻したあとの、中心から各点までの距離と半径の食い違いが、半径の `1e-4` を超えるとき(非常に大きな座標の丸め)も作らない。理由を表示して、同じ段階のまま待つ。
- **ゴム紐:** `PreviewShape` は、折れ線(`polyline`)のほか、円(`circle`)と円弧(`arc`)を持つ。画面は、拡大しても多角形にならないよう、キャンバスの円弧で描く。
- **保存の Phase への申し送り:** 円弧の角度は、ラジアンで持っている。DXF の ARC は、度(DXF の 50・51 の値)で、反時計回り。円(CIRCLE)の色は、ほかの新しい図形と同じく、レイヤー色の数値(保存では BYLAYER へ戻す)。

### ダイナミック入力と数値入力(Phase 6)の約束事

- **単位と表示:** 単位は mm 固定。表示は小数1桁(`formatCoordinate`、`formatDynamicValue`、ステータスバーの `formatMm`)。**内部の値は丸めない**(表示のときだけ丸める)。角度は度(+X方向が0、反時計回り)で、0以上360未満にそろえる。
- **入力の受け口は、コマンドライン1つ。** カーソル付近の表示(`components/DynamicInput.tsx`)は、打っている途中の値を映すだけで、入力欄ではない(マウス操作は通す)。点を待っている間に、フォーカスが入力欄に無くても、数字・`.`・`-` のキーを押すと、入力欄へ移って打ち始める。
- **点の決め方は、`core/commands/dynamicInput.ts`(純粋な関数)。** 段階の種類で、入力できる項目が決まる。
  - `absolute`: 基準点が無い(1点目)。X・Y。
  - `polar`: 基準点がある(2点目以降)。長さ・角度(基準点からの極座標)。
  - `distance`: 数値だけを待つ段階(円の半径・直径)。長さだけ。
  - 打っていない項目は、カーソルの値を使う(長さだけ打って Enter なら、角度はカーソルの向き)。
- **キー操作:** 数値を打って Tab で、その項目の値を確定し、次の項目へ(Shift+Tab で前へ)。Enter で、確定した値と、打っている値から点を作って、`CommandSession.submitPoint()` に渡す(クリック・座標入力と同じ入口)。座標(`1000,500`・`@…`)・キーワード・コマンド名・空の Enter(確定した値が無いとき)は、これまでどおりコマンドへ渡す。Esc は、コマンドの取り消し。
- **基準点:** `ActiveCommand.basePoint` が、段階の基準点(相対座標・極座標・長さ/角度の基準)。段階が宣言する(`PromptBase.basePoint`)。円弧の通過点・終点の段階にも設定した。中心・始点・終点の円弧の終点は、方向だけが意味を持つので、基準を中心にした(相対座標 `@` も、この段階では中心から)。
- **確定した値の寿命:** コマンドの状態が進む(`commandRevision` が変わる: 点の指示、キーワード、終了)たびに捨てる。
- **見えているものと、確定するものを一致させる:** 打っている値と、確定した値を、カーソルの点に当てはめた「実効の点」(`applyTypedValues`)を、ゴム紐(`previewAt`)・クリックでの指示・カーソル付近の表示専用の項目の、すべてで使う。例: 長さ 70 を確定してからクリックすると、クリックした向きに、長さ 70 の点になる(ゴム紐に見えていたとおり)。
- **読み取れない値:** Enter では、理由を表示して同じ段階で待つ(入力欄は、これまでどおり空になる)。Tab では、確定せず、項目も動かさず、打った文字も残す(直せるように。前に確定した値で、誤って確定しないため)。
- **含めていないもの:** Grip 編集中の数値入力(Phase 18)、ORTHO・POLAR などの拘束(Phase 8。ダイナミック入力は、カーソルの点から計算するので、後から組み合わせられる)、ダイナミック入力欄での `U`・`C`・`D` のキーワード入力、ON/OFF の切り替え(常に ON)。

### Snap(Phase 7)の約束事

- **種類(`core/snap/snapTypes.ts`):** 端点・中点・交点・中心・四半円点・垂線・接線・近接・延長(図形への吸着。OSNAP)と、グリッド(格子点への吸着。SNAP)。Snap の計算は `core/snap/` に独立していて、Renderer には実装しない(Renderer は、目印を描くだけ)。
- **優先順位:** 図形への吸着のうち、カーソルに最も近いもの → 無ければ近接 → 無ければグリッド(グリッドには許容距離が無く、いちばん近い格子点)。距離が同じときは、これまでの種類(端点・中点・交点)が、新しい種類に勝つ(これまでの結果を変えないため。`GENERATORS` の並びがその規則)。
- **呼び出し(`findSnapPoint`):** 既存の引数はそのまま。`options.enabledTypes` を指定しないと、これまでどおり(端点・中点・交点。近接は `nearestToleranceWorld` を指定したとき)。指定すると、含まれる種類だけを調べる。`fromPoint`(垂線・接線の基準の点)、`gridSpacing`、`extensionAcquireWorld` も options で渡す。
- **基準の点:** 垂線・接線は、`fromPoint`(作図中の直前の点など。`ActiveCommand.basePoint`、測定では1点目)があるときだけ出る。
- **交点の精度:** 線どうしは線分の交点。円・円弧が絡むもの(線×円・円弧、円・円弧どうし)は、折れ線の近似ではなく、解析的に求める(`core/geometry/curves.ts`)。円弧は、角度の範囲内の交点だけ。楕円・スプラインは、これまでどおり折れ線の近似。
- **中心の探し方:** 円は、カーソル付近の図形から。円弧・楕円は、外接の矩形がカーソルから離れていても中心が近いことがあるため、中心の x 座標で並べた索引(空間索引ごとに1回だけ作る。図面が変わるたびに作り直される)を二分探索し、y でも絞る。取り出した図形は、図面の並びの順にそろえる(同じ距離の候補があるとき、索引の有無で選ばれる候補が変わらないように)。
- **数値の安定性(Codex レビューでの修正):** 線分と円の交点は、判別式ではなく、中心から直線までの距離と、垂線の足の位置で求める(非常に長い線分でも、離れた線を接線と取り違えない・交点を失わない)。円どうしの接する許容は、小さい方の円の半径に合わせる(大きな円の内側の、隙間のある小さな円に、架空の接点を作らない)。格子の表示は、格子の番号が 2^53 以上(正確な整数として数えられない)のときは描かない(ループが終わらなくなるため)。
- **延長:** 線・開いた折れ線の端の線分と、円弧の続き(同じ円)。端点がカーソルから acquire の距離(画面上150px)以内にある図形だけが対象で、端点より先の側だけ(図形そのものの上は、近接)。
- **四半円点:** 円・円弧は 0°・90°・180°・270°(円弧は範囲内のものだけ)。楕円は、長軸・短軸の端点(回転を反映)。
- **設定(`core/snap/snapSettings.ts`):** OSNAP・SNAP・GRID のオン・オフ、種類ごとのオン・オフ、格子の間隔(mm。0.001〜1,000,000)。初期値は、端点・中点・交点・中心・四半円点・近接がオン、垂線・接線・延長がオフ、グリッドの表示・吸着はオフ、間隔は 10 mm。このブラウザの localStorage に保存する(`utils/snapSettingsStorage.ts`。保存できなくても動きは変わらない。読み戻した値は、`normalizeSnapSettings` で検証する)。
- **切り替えの入口:** ステータスバーのボタン(GRID・SNAP・OSNAP・設定)、F7・F9・F3、コマンドライン(`GRID`・`SNAP`・`OSNAP`)は、どれも `toggleSnapSetting` の依頼を、同じ実行(`executeRequest`)で動かす。ボタンと F キーは、実行中のコマンドを終わらせない(コマンドラインから動かすのは、コマンドが動いていないとき)。
- **目印と格子の表示(`cad-view/renderer/snapMarker.ts`):** 種類ごとに形(端点=四角、中点=三角、交点=×、中心=円、四半円点=ひし形、垂線=直角、接線=円と接線、近接=砂時計、延長=点線の十字、グリッド=十字)と名前を描く。格子点は、画面上の間隔が 8px 以上のときだけ描く(吸着は、設定どおり)。
- **含めていないもの:** 一時的な Snap の指定(`END` などの入力、Shift+右クリック)、レイヤーごとの対象指定(Phase 17)、ORTHO・POLAR・OTRACK(Phase 8。ステータスバーのボタンも、そこで足す)。
- **設定を変えたとき:** マウスが動かなくても、いまのカーソル位置で、吸着・目印・ゴム紐・座標表示を作り直す(F3 で OSNAP をオフにしたとき、古い吸着位置のゴム紐が残らないように)。F3・F7・F9 は、キーの繰り返し(押し続け)では切り替えない。
- **性能(19万図形の実図面):** 既定の設定で 1 回あたり 約0.03〜0.1 ms(これまでの 4 種類と同程度)。全種類で 約1 ms。図面を変更したあと、最初の Snap だけ、中心の索引を作るため約30〜40 ms かかる(図面の変更時の、空間索引の再構築 約41 ms と同程度)。

### トラッキング(Phase 8)の約束事

- **カーソルの点を決める段階(`core/tracking/resolveCursor.ts`)。** CadCanvas は、これを呼ぶだけ。順に、(1) 図形への吸着(端点・中点・交点・中心・四半円点・垂線・接線・延長。近接を除く)→ (2) トラッキング(ORTHO・極トラッキング・OTRACK)→ (3) 近接 → (4) グリッド。前の段階で決まれば、あとの段階は調べない。トラッキングが全部オフで取得した点も無ければ、これまでの Snap(`findSnapPoint` 1回)と、完全に同じ結果になる(ランダムなテストで確認)。
- **ORTHO:** 基準点があるとき、カーソルを、基準点からの水平・垂直(縦横の距離の大きい方。同じなら水平)に、常に揃える。図形への吸着(端点など)が見つかれば、そちらが優先(ORTHO の軸の上に無くてもよい)。ORTHO 中は、近接には吸着しない(軸の上の点を優先)。SNAP(グリッド)がオンなら、軸の上で、いちばん近い格子点にする。取得した点(OTRACK)からの補助線と軸が交わる所では、その交点。基準点が無い1点目には、効かない。
- **POLAR(極トラッキング):** 基準点から、角度の刻み(5・10・15・18・22.5・30・45・90°)の方向の半直線に、カーソルが画面上10px以内に近づいたら、その方向に揃える(基準点に近すぎるとき=許容距離以内では、揃えない)。トラッキング間隔(mm)が正なら、基準点からの距離を、その倍数に揃える(0 以下になるときは揃えない)。揃えた角度を、点の近くに表示する。
- **OTRACK:** 吸着点(端点・中点・交点・中心・四半円点)の上に、カーソルを約0.3秒(`OBJECT_TRACKING_DWELL_MS`)とどめると、その点を取得する(最大3点。古いものから消える)。同じ点にもう一度とどめると、取得を解除する。取得した点からは、水平・垂直(POLAR がオンなら角度の刻み。基準点が無くても)の両側へ延びる直線が、補助線になる。2本の補助線(取得した点どうし、極トラッキングの線と取得した点の線、ORTHO の軸と取得した点の線)の両方に近づいたら、その交点に揃える(いちばん近い交点)。取得した点は、コマンドの状態が進んだとき(点の指示・終了など。`trackingResetKey`)、点の指示も測定もしていないとき、OTRACK をオフにしたときに捨てる。
- **取得点の管理(`core/tracking/acquisition.ts`):** とどめ時間の計測・取得・解除・最大数・全部捨てる、をまとめた `ObjectTrackingAcquirer`。時間は、外から渡す `Scheduler`(画面では `window.setTimeout`、テストでは仮想の時計)で計る。同じ点かの判定は、座標の誤差を許す(同じ交点が、別の線分の組から、わずかに違う座標で返されても、同じ点)。取得した点が変わると、再描画して、いまのカーソル位置で作り直す。測定の点を確定するたびにも、捨てる(測定は、コマンドの状態が変わらないため)。画面を閉じるときは、計測だけを止める。
- **トラッキング間隔の下限:** 0(揃えない)か、0.001〜1,000,000 mm。極端に小さい間隔では、距離を間隔で割った値が溢れて、座標が有限でなくなるため(保存された値も、同じ検証。揃えた結果が有限でないときは、揃えない)。補助線の交点には、間隔の丸めを適用しない(適用すると、2本の線から外れる)。
- **補助線の描画:** 補助線は、画面(ビューポート)と交わる区間だけを描く(起点が画面から非常に遠くても、画面にかかる部分が出る)。
- **排他:** ORTHO と POLAR は、同時にオンにできない(片方をオンにすると、もう片方がオフになる。`toggleTracking`)。OTRACK は、どちらとも共存できる。
- **ORTHO・POLAR の基準点:** 垂線・接線と同じ。作図中は `ActiveCommand.basePoint`、測定中は1点目。
- **ダイナミック入力(Phase 6)との関係:** 揃えた点が、そのまま入力の「カーソルの値」になる。長さだけを打って Enter なら、揃えた方向に、その長さの点ができる(直接距離入力)。
- **設定:** `core/tracking/trackingSettings.ts`。ORTHO・POLAR・OTRACK(初期値は、3つともオフ)、角度の刻み(初期値 45°)、トラッキング間隔(初期値 0=なし)。このブラウザの localStorage に保存する(`utils/trackingSettingsStorage.ts`。読み戻した値は `normalizeTrackingSettings` で検証し、ORTHO と POLAR が両方オンなら ORTHO だけ残す)。
- **切り替えの入口:** ステータスバーのボタン(仕様の順: GRID・SNAP・ORTHO・POLAR・OSNAP・OTRACK)、F8=ORTHO・F10=POLAR・F11=OTRACK(キーの繰り返しでは切り替えない。F11 は、ブラウザの全画面の切り替えと重なる環境がある)、コマンド `ORTHO`・`POLAR`・`OTRACK`。どれも `toggleTrackingSetting` の依頼を、同じ実行(`executeRequest`)で動かす。ボタンと F キーは、実行中のコマンドを終わらせない。
- **描画(`cad-view/renderer/trackingRender.ts`):** 補助線は、水色の破線で、画面の端まで延ばす(ORTHO だけのときは、描かない)。取得した点は「＋」。極トラッキングで揃えたときは、角度を点の近くに出す。
- **含めていないもの:** Shift キーを押している間だけの一時的な ORTHO、任意の角度の追加、直前の線分からの相対角度での極トラッキング、一時的な Snap の指定(`END` など)、Grip 編集中のトラッキング(Phase 18)。
- **Snap の修正(Phase 8 の確認中に見つけた):** 楕円・スプラインは折れ線に近似していて、その頂点(隣り合う線分が接する点)が「交点」として吸着していた。同じ図形の、隣り合う線分(続けて並んでいる、または、閉じた図形の最初と最後)が、共有する頂点で接しているだけのものは、交点として扱わない(本当の交点、隣り合わない線分が同じ点で交わる点=折れ線が自分自身と交わる点は、これまでどおり)。

ツールバーのボタン、ショートカット(F・M)、コマンドライン、図面のクリックは、どれも `CommandSession` という1つの入口からコマンドを動かします。

### 図形の編集(Phase 9)の約束事

対象は、移動(MOVE・MO)・コピー(COPY・CO・CP)・回転(ROTATE・RO)・削除(DELETE・E・DEL。Delete キー)。1回の操作は、1つの変更(`ChangeSet`)にして `DocumentSession` に渡すので、何個の図形を動かしても、履歴は1段階(Undo は1回)。

- **編集してよいかの判断(`app/document/editability.ts`):** 新しく描いた図形(ID が `n<番号>`)は、常に編集できる。取り込んだ図形は、最上位の図形だけ編集できる。ブロック(INSERT)の中身・寸法は、読み取り専用(`origin.nested = 1`)。元データとの対応づけに失敗した図面(`recordOfParserEntity === null`)は、取り込んだ図形を編集できない。`io/` の分類は、画面の側(`App.tsx` の `editabilitySourceOf`)が `EditabilitySource` に直して渡す(`app/` は `io/` を読めないため)。図面の読み込み中は、編集コマンドを始められない。
- **選択の扱い(`selection` ステップ):** 先に選択してあれば、それを使う。無ければ「図形を選択してから、Enter」と促し、普通のクリック・ボックス選択で選ばせて、Enter で確定する(コマンドラインへの文字入力は、選択ステップでは受け付けない)。編集できない図形が混ざっていたら、編集できるものだけを対象にして、除いた数と理由をコマンドラインに出す。1個も編集できなければ、コマンドは始まらず、理由を出す。
- **移動・回転の適用(`app/document/editing.ts`):** 図形を、剛体変換(移動・回転。`core/geometry/transform.ts` の `Affine2D`)で動かした新しい図形に置き換える(`replaceEntitiesChangeSet`)。ID・レイヤー・色・描画順は変わらない。形以外の属性(ポリラインの頂点の bulge など)は、そのまま。移動量が0・回転角が0度は、何もせず理由を出す。剛体でない行列は、Phase 10 で、相似変換(拡大縮小・鏡像)まで広げた(下の「形を変える編集」)。
- **コピー:** 繰り返して複写する(位置を指示するたびに、1つ複写。Enter・Esc で終了。`U` で直前の複写を取り消す)。終了時に、全部を1つの変更として確定する(Esc でも、それまでの分は確定。途中でコマンドが終わったときも)。複写は新しい図形(`n<番号>`)で、描画順の末尾に、もとの前後関係を保って加える。
- **回転:** 基点 → 角度。角度は、数値入力(度)、または、点の指示(基点からの角度)。ダイナミック入力は「角度」の欄だけを出す(`DynamicMode = "angle"`)。数値入力は、点の入力ステップの `numberMeaning: "angle"` で、長さではなく角度として読む。
- **ゴム紐(`core/commands/entityPreview.ts`):** 選択した図形の移動後の形を、白い破線で出す。図形が多い(300個超)ときは、全体を囲む長方形だけを出す(性能のため)。
- **元データとの対応(`sourceRecord`。保存の Phase への申し送り):** 取り込んだ図形のポリラインは、膨らみ(bulge)を展開した点列に、スプラインは、折れ線に変換されている。保存のときは、この展開後の座標を元の記録に書き戻せないので、「元の記録のID」と「取り込み時から、いま(編集後)までの剛体変換の行列」を、図形に持たせる(`CadEntity.sourceRecord = { id, matrix }`)。移動・回転のたびに、行列を合成する(`composeAffine`)。保存の Phase では、元の記録の座標に、この行列を適用して書く(bulge は、剛体変換で変わらない)。取り込んだ図形の複写も、元の記録への対応(単位行列から)を持つ(保存のとき、元の記録の属性を引き継いで、新しい記録を作る)。新しく描いた図形は、元の記録が無いので、持たない。Undo・Redo は、図形そのもの(`sourceRecord` を含む)を戻す。
- **描画順(TOFRONT・TOBACK)の拡張:** 取り込んだ最上位の図形にも、効くようにした(Phase 4 では、新しく描いた図形だけ)。ブロックの中身・寸法は、これまでどおり対象外(理由を出す)。
- **Delete キー:** コマンドが動いておらず、選択があり、入力欄で文字を打っていないときだけ、`DELETE` を動かす。
- **変更の適用の高速化(`core/history/apply.ts`):** 削除だけ(位置が大きい順)・追加だけ(位置が小さい順)の変更(多数の図形の削除と、その Undo)は、1回の走査で適用する。1件ごとに配列を詰め直す方式では、19万図形の実図面で、散らばった10万個の削除が約34秒かかった(Phase 9 の測定で判明)。条件に合わない変更は、これまでどおり1件ずつ適用する(エラーの文言も同じ)。両者が同じ結果になることを、ランダムな変更のテスト(`applyBulk.test.ts`)で確かめている。
- **性能(実図面。`src/regression/edit.perf.regression.test.ts`。時間は参考値で、失敗にしない):** 10万個の図形の移動 約0.6秒・Undo 約0.1秒・削除 約0.3秒(19万図形の実図面)。1,000個の移動は 約0.1秒。選択のゴム紐は、300個を超えると外形だけなので、図形数によらず約25ms 以下。
- **桁あふれの拒否と安全側の判断(Codex レビューでの修正):** 有限な座標が、変換で有限でなくなる(例: `1e308` の図形を `1e308` 動かす)ときは、変換そのもの(と、`sourceRecord` の合成結果が有限でないとき)を拒否する(1つでも失敗したら、全体を何もせずに拒否。COPY は、全部の形ができてから ID を払い出す)。もともと有限でない座標(壊れたデータ)は、これまでどおり、そのまま扱う。編集可否の分類が、図形の添字と食い違う(範囲外・0/1 以外の値)ときは、編集できる側ではなく、編集できない側に倒す。90°の倍数の判定は、小さい角度(|角度| < 1000 ラジアン)に限り、回転角(度)は 360 で割った余りにしてから使う(巨大な角度でも、精度を保つ)。COPY のゴム紐は、指示済みのコピーの形を、段階ごとに1回だけ作る。
- **回転角の許容:** 90° の倍数から 1e-12 ラジアン(約 6e-11 度)以内の角度は、ぴったりの値にそろえる(座標に誤差を入れないため)。そのため、これより小さい角度の回転は、「回転なし」として拒否される。
- **含めていないもの:** ROTATE の「参照」・「コピー」オプション、COPY の「配列」・「変位」、Grip 編集(Phase 18)、保存(Phase 21・22。編集は、まだファイルに保存されない)。
### 形を変える編集(Phase 10)の約束事: MIRROR・SCALE・STRETCH

エイリアスは MI・SC・S。1回の操作は、Phase 9 と同じく、1つの変更(`ChangeSet`)で、Undo は1回。ブロックの中身・寸法は読み取り専用(除いて、理由を出す)。

- **相似変換(`core/geometry/transform.ts`):** 変換を「剛体(移動・回転)」から「相似変換(移動・回転・一様な拡大縮小・鏡像)」に広げた(`isSimilarity`)。非一様な拡大縮小・せん断・つぶれる変換・非有限な行列は、拒否する。移動・回転だけの変換の計算は、これまでと完全に同じ(別の経路 `transformSimilar` は、倍率や鏡像を含むときだけ通る)。`scaleMatrix(基点, 倍率)`、`reflectionMatrix(軸の2点)`(水平・垂直・45度の軸では、成分がぴったりの値)。
- **図形ごとの扱い(相似変換):** 円・円弧・楕円の半径と、文字の高さには倍率を掛ける。線の太さ・破線の間隔は、変えない。円弧は、鏡像で向きが逆になるので、始点と終点を入れ替える(反時計回りのまま)。楕円の鏡像は、共役な半径から標準形に直す(`ellipseTransform.ts` を再利用)。**文字は、鏡像でも反転させない**(挿入点だけを動かし、向きは変えない)。倍率だけの変換は、角度の値に触らない。桁あふれ(有限な値が有限でなくなる)は、Phase 9 と同じく、全体を拒否する。
- **MIRROR:** 選択 → 軸の2点 →「元の図形を削除しますか? [はい(Y)/いいえ(N)] <N>」(文字で答える。Enter = いいえ)。いいえ=鏡像の複写(新しい図形。`copyEntities`)。はい=元の図形を、鏡像に置き換え(ID・描画順は保つ。`transformEntities`)。軸の2点が同じ点なら、拒否。
- **SCALE:** 選択 → 基点 → 倍率(数値)。`R` で「参照の長さ(数値、または2点)→ 新しい長さ(数値、または、基点からの距離をクリック)」。倍率 = 新しい長さ ÷ 参照の長さ。倍率は、0 より大きく、`1e-6` 以上 `1e6` 以下(1 は何も変わらないので、拒否)。倍率の段階では、クリックは受け付けない(数値で入力する。mm の座標がそのまま倍率になるのを避けるため)。倍率・参照の長さの段階は、`numberMeaning: "plain"`(ダイナミック入力は出さず、コマンドラインで入力)。新しい長さの段階は、ゴム紐が、カーソルまでの距離に追従する。
- **STRETCH:** 交差窓の2点 → 基点 → 移動先。選択は使わない。窓にかかる図形(範囲が窓と重なる、編集できる図形)を、全図形から探す(`AppEditing.findInWindow`。10万図形でも 約20〜35ms)。図形ごとの扱いは `core/geometry/stretch.ts`: 直線=窓の中の端点だけ動く、折れ線・スプライン=窓の中の頂点だけ動く(全部なら、図形ごと移動)、円・点・文字=中心(挿入点)が窓の中なら図形ごと移動、円弧・楕円=全体が窓の中のときだけ図形ごと移動(一部だけ入っているものは対象外で、数を知らせる)。窓の辺の上は、中。ゴム紐は、動かした後の形(候補が 300 個を超えると、移動した窓の枠だけ)。
- **元データとの対応(保存の Phase への申し送り):**
  - `sourceRecord.matrix` は、相似変換(倍率・鏡像を含む)になりうる。保存の Phase は、図形の種類ごとに、元の記録へ適用する規則を持つこと: 円弧は、鏡像で始点・終点の角度を入れ替える。ポリラインの bulge は、鏡像で符号を反転する(拡大縮小では、bulge は変わらない)。円・円弧・楕円は半径に倍率を掛ける。文字は、高さに倍率を掛け、**鏡像では反転させない**(挿入点だけを変換)。
  - **STRETCH で頂点が個別に動いた図形は、行列では表せない。** 取り込んだ折れ線は、円弧の膨らみ(bulge)が展開済みの点列なので、頂点を動かした結果は、元の記録の頂点と対応しない。そのため `SourceRecord.reshaped: true` の印を付ける。保存では、印のある図形を、matrix を適用するのではなく、**いまの形で元の記録を置き換えて書く**(折れ線は、展開後の点列になる。見た目は同じ)。印は、あとで移動・コピーしても、引き継がれる(matrix は合成される)。図形ごと動いた(窓に全体が入った)図形には、付けない(平行移動の行列の合成だけ)。
- **含めていないもの:** 非一様な拡大縮小・せん断、SCALE の「コピー」、MIRROR の文字の反転の選択(MIRRTEXT)、STRETCH での円・円弧・楕円の部分変形、選択済みの図形を使った STRETCH、Grip 編集(Phase 18)、保存(Phase 21・22)。
## 新しいコードを置く場所の決め方

1. 画面に関係なく、CAD としての計算や状態の変更か → `core/`
2. ファイル形式(DXF、DWG、将来の独自形式・PDF)に関わるか → `io/`
3. 「どのコマンドが、何をするか」など、画面に関係しないアプリの動きか → `app/`
4. 画面の部品や、マウス・キーボードの扱い、ワーカーの起動か → 画面の側(今は `cad-view/`、`components/`、`App.tsx`)

迷ったら、下の層(`core/`)に置けないかを先に考えます。下の層に置いたほうが、テストしやすく、壊れにくくなります。

## 今後の方針: 編集の結果を保存へ渡す方法(Phase 2・3・保存の Phase で具体化)

編集(コマンド、Undo)は `core/` に、保存(元データへの差分の適用)は `io/` にあります。`core/` は `io/` を読み込めないので、次の形でつなぎます。

- `core/` は、**ファイル形式に依存しない「変更の内容」**(追加・削除・変更した図形のID と、変更前後の図形)を作って返す。Undo も、この変更の内容を記録する。
- `io/` は、その「変更の内容」を受け取り、図形のID から元データの記録を引いて、差分(削除・差し替え・追加)に変換して適用する。
- 両者を呼び出して結びつけるのは、画面の側(将来は、画面と中核の間に置く「アプリの層」)。

## まだ整理していないもの(後の Phase で行う)

- 画面の側(`cad-view/`、`components/`)は、今の場所のままです。画面を作り直す Phase で、`render/`(描画)と `ui/`(React の部品)に分ける予定です。
- `core/model/convert.ts` は、範囲の計算を引数で受け取っています(Phase 1a で core の外にあったため)。Phase 1c で同じ `core/` に移ったので、直接呼ぶ形に簡単にできます(処理を変えないため、今はそのまま)。
