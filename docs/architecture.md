# フォルダの役割と依存の向き

2D CAD Viewer を本格的な 2D CAD へ段階的に広げるための、フォルダの役割と規則です(Phase 1c で整理)。
規則は自動テスト `src/architecture.test.ts` で確認しています。違反すると `npm test` が失敗します。

## 全体の形

```
画面(React)  App.tsx / components/ / cad-view/
     │
     ▼
app/  アプリの動き(コマンドなど。画面の機能は使わない)
     │
     ▼
io/  ファイル形式の読み書き(DXF・DWG、ワーカーの中の処理)
     │
     ▼
core/  CADの中核(モデル・幾何・選択・スナップ・測定・表示の座標)
     │
     ▼
types/  共通の型(CadEntity など)
```

- **矢印の向き(上から下)にだけ、読み込んでよい**のが原則です。下の層は、上の層を知りません。
- **下の層へは、1つ飛ばしでも直接読み込んでよい**です。たとえば、画面から `core/` を直接使ってかまいません(`CadCanvas` は、選択やスナップを直接使っています)。

## 各フォルダの役割

| フォルダ | 役割 | 読み込んでよいもの | 使ってよい実行環境の機能 |
|---|---|---|---|
| `src/core/` | CAD の中核。画面にも、ファイル形式にも依存しない。 | `core/`、`types/` だけ。外部パッケージは使わない。 | ECMAScript の標準だけ(ブラウザの `window`・`document`・Canvas も、Node の機能も使わない) |
| `src/io/` | ファイル形式の読み書き。DXF・DWG の解析、元データの保持、**ワーカーの中で動く処理**。 | `io/`、`core/`、`types/`、決めたパッケージ(`dxf-parser`、`@mlightcad/libredwg-web`)。画面は読み込まない。 | ECMAScript の標準と、ワーカーで使える機能(`TextDecoder`、`WebAssembly`、`console` など)。DOM(画面)は使わない。 |
| `src/app/` | アプリの動き。コマンド(名前・別名・段階・依頼)など、画面と中核の間で「何をするか」を決める。React や画面の機能は使わない(だから単体テストできる)。 | `app/`、`core/`、`types/` だけ。外部パッケージは使わない。(`io/` は、保存とつなぐ段階で必要になったら、規則の変更として加える) | ECMAScript の標準だけ |
| `src/types/` | 共通の型。**型の宣言だけ**を置く(値・関数・クラスは置かない)。 | `types/` の型だけ(`import type`)。 | － |
| `src/cad-view/`、`src/components/`、`App.tsx`、`src/hooks/`、`src/utils/`、`src/devHooks.ts` | 画面(React と Canvas の描画)。**ワーカーを起動・管理するのも画面の側**(`App.tsx`)。 | すべて。ほかの層からは読み込まれない。 | すべて |

### 例外

- **DWG 変換の WASM:** `io/` は、`node_modules/@mlightcad/libredwg-web/wasm/` のフォルダだけを、相対パスで読み込んでよいです。パッケージが、このファイルを公開範囲(`exports`)に含めていないためです。`node_modules` のほかの場所を相対パスで読み込むことはできません。

### 規則の対象外(テスト用のもの)

次のものは、規則の検査の対象外です(何を読み込んでもよい)。その代わり、**本番のコードから、これらを読み込むことはできません。**

- テスト本体(`*.test.ts`、`*.test.tsx`)
- テスト用の補助(`testHelpers.ts`)
- 回帰テスト(`src/regression/`)、E2E(`e2e/`)

## 検査の方法

文字の検索ではなく、TypeScript 自身を使って検査します。そのため、コメント、文字列、変数名(`document` という名前のCADドキュメントなど)に惑わされません。

- **依存の向き:** 構文解析で、`import`、`export … from`、動的 `import()`、型の `import("…")`、`new URL("…", import.meta.url)` を取り出して調べます。読み込む先を文字列で直接書いていない動的 `import()` は、違反とします。
- **実行環境の機能:** `core/` と `types/` は「ECMAScript の標準の型だけ」で、`io/` は「ECMAScript とワーカーの型だけ」で、型チェックします。使ってはいけない機能(`window`、`document.createElement`、`localStorage`、Canvas など)を使うと、TypeScript が「見つからない」として検出します。

## `core/` の中身

| フォルダ | 内容 |
|---|---|
| `core/model/` | ドキュメントモデル(図形の一覧、ID、レイヤー)、描画用モデルとの変換 |
| `core/geometry/` | 幾何(距離、交点、行列、スプライン、ポリラインの膨らみ、楕円の変換、図形の頂点と線分) |
| `core/style/` | 線種(破線のパターン)、線の太さ |
| `core/spatial/` | 空間索引(図形の範囲、格子) |
| `core/selection/` | 選択(クリック、窓、交差) |
| `core/snap/` | スナップ(端点、中点、交点、最近点) |
| `core/measurement/` | 測定 |
| `core/view/` | 表示の拡大と位置(カメラ) |

| `core/commands/` | コマンドの登録簿、コマンドの進め方(段階)、実行の状態、座標入力の読み取り、入力の履歴(Phase 2) |
| `core/history/` | 図面の変更の内容(`ChangeSet`: 追加・削除・置き換え・描画順の入れ替え)、原子的な適用、反転、Undo/Redo の履歴(上限200段階)、いまの状態の識別番号(未保存の判定用)(Phase 3・4) |

### 変更の内容(`ChangeSet`)の約束事(Phase 3)

- 変更は、**必ず `ChangeSet` として** `DocumentSession.apply()` を通す。図面(`CadDocument`)を直接書き換えない。
- 位置(`index`)は、その変更を適用する直前の、描画順の配列での位置。1つの `ChangeSet` の中の変更は、書かれた順に適用する。
- 削除・置き換えは、その位置にある図形が「同じオブジェクト」であることを確かめる。一致しなければ、何も変えずに失敗する(図面が履歴と食い違ったまま進むことを防ぐ)。
- 新しい図形のID(`n<番号>`)は、`DocumentSession.allocateEntityId()` で払い出す。Undo しても払い出し番号は戻らず、同じIDを別の図形に使い回さない。
- コマンドは `addEntitiesChangeSet`・`removeEntitiesChangeSet`・`replaceEntitiesChangeSet` で変更を作る(位置の計算を間違えないため)。
- 描画順の入れ替え(`move`)は、「from の位置の図形を取り出して、取り出したあとの配列の to の位置に入れる」。最前面・最背面への移動は `moveToFrontChangeSet`・`moveToBackChangeSet` で作る(指定した図形どうしの前後関係は保つ)。
- **保存の Phase への申し送り:**
  - 新しく描いた図形は、DXF の ENTITIES 区画に記録として挿入する。描画順の入れ替えは、記録の位置の入れ替え(取り出して、挿入)として扱う。いまの差分の適用(`io/dxf/patch.ts`)は、置き換えと削除だけなので、挿入を足す必要がある。
  - 新しい図形の色は、レイヤー色を数値にして持っている(取り込んだ図形と同じ扱い)。保存では、レイヤー色の指定(BYLAYER)に戻す。
- **編集系のコマンド(Phase 4以降)の約束:** 展開済みのブロックの図形や、寸法など「読み取り専用」の図形は、編集しない。判断に使う分類(editable / readOnly)は `io/` にあるので、`app/` の層が受け取ってコマンドに渡す(`core/` は `io/` を読み込めないため)。

## `io/` の中身

| フォルダ | 内容 |
|---|---|
| `io/dxf/` | DXF の解析(`DxfParserAdapter`)、文字コード、レイヤーの表、DWG→DXF の変換、ワーカーの中の処理、元データの索引と差分の適用(保存の土台) |

## `app/` の中身

| フォルダ | 内容 |
|---|---|
| `app/commands/` | アプリに最初から入っているコマンド(OPEN・CLOSE・FIT・MEASURE・FULLSCREEN・UNDO・REDO・LINE・PLINE・RECT・TOFRONT・TOBACK・ID)。コマンドが返す「アプリへの依頼」(`AppRequest`)の型と、コマンドを始める時点の状態(`AppCommandContext`: 図面が開いているか、描く先、ID の払い出し)。依頼を実際に実行するのは画面の側(`App.tsx`)。 |
| `app/document/` | `DocumentSession`(開いている図面のドキュメントと変更の履歴を持ち、変更を購読者に知らせる。未保存の判定 `isDirty` と `markSaved()` を持つ)、元に戻す結果のメッセージ、ドキュメントから描画用モデルを作る処理、選択中の図形の描画順の変更(`reorderSelection`)。 |
| `app/drawing/` | 作図の部品。新しい図形(線・ポリライン・長方形)を作る処理と、描く先(現在のレイヤー)の決定。 |

### 作図(Phase 4)の約束事

- 作図コマンドは、図面を直接変更せず、「図形を追加する」依頼(`addEntities`)を返す。画面の側が `DocumentSession.apply()` を通して適用する。**1つのコマンドで描いた分は、1つの Undo の単位**になる。
- 点を順に指示するコマンド(LINE・PLINE)は、Enter(空)と Esc のどちらでも終了し、描いた分を確定する(`onCancel`)。`U` で1点戻す、`C` で閉じる(3点以上)。作図中の Ctrl+Z は `U` として働く。
- ゴム紐(描いている途中の仮の図形)は、コマンドの段階が返す形式に依存しない折れ線(`PreviewShape`)を、画面が重ねて描くだけ。図面のデータは変えない。
- 描く先は「現在のレイヤー」(レイヤー欄で選ぶ。初期値はレイヤー `0`)。非表示のレイヤーには描かない。新しい図形の色は、そのレイヤーの色。
- 描画順: 新しい図形は常に最前面(末尾)に追加する。`TOFRONT`・`TOBACK` は、この作業で新しく描いた図形(ID が `n<番号>`)だけが対象。取り込んだ図形の順序変更は、編集してよい図形かの分類(io の editable / readOnly)をアプリの層へ渡す仕組みと一緒に、Phase 9 で行う。
- 未保存の保護: 変更があると「未保存の変更あり」と表示し、図面を閉じる・別の図面を開く・ページを閉じる(再読み込み)ときに確認を出す。
  - 確認は、画面の状態ではなく `DocumentSession.isDirty` を直接読んで判断する(作図の途中で「閉じる」を押すと、描きかけの図形を確定してから閉じる依頼が続くため、画面の状態はまだ古い)。
  - 描きかけで、まだドキュメントに入っていない図形(LINE・PLINE で2点以上)も、ページを閉じる前の確認の対象にする(`ActiveCommand.hasPendingChanges`)。
  - 新しい図面を読み込んでいる間は、いまの図面を変更しない(作図コマンドは始まらず、元に戻す・やり直し・描画順は拒否する)。読み込みが終わると、いまの図面と変更は置き換えられるため。
  - 保存の Phase では、保存を始める時点で `saveToken` を控え、成功したら `markSaved(token)` を呼ぶ(保存している間に編集が進んでも、保存できた状態だけを保存済みにするため)。`markSaved` と、履歴の破棄(`reset`)は、購読者に状態の変化を知らせる。

ツールバーのボタン、ショートカット(F・M)、コマンドライン、図面のクリックは、どれも `CommandSession` という1つの入口からコマンドを動かします。

## 新しいコードを置く場所の決め方

1. 画面に関係なく、CAD としての計算や状態の変更か → `core/`
2. ファイル形式(DXF、DWG、将来の独自形式・PDF)に関わるか → `io/`
3. 「どのコマンドが、何をするか」など、画面に関係しないアプリの動きか → `app/`
4. 画面の部品や、マウス・キーボードの扱い、ワーカーの起動か → 画面の側(今は `cad-view/`、`components/`、`App.tsx`)

迷ったら、下の層(`core/`)に置けないかを先に考えます。下の層に置いたほうが、テストしやすく、壊れにくくなります。

## 今後の方針: 編集の結果を保存へ渡す方法(Phase 2・3・保存の Phase で具体化)

編集(コマンド、Undo)は `core/` に、保存(元データへの差分の適用)は `io/` にあります。`core/` は `io/` を読み込めないので、次の形でつなぎます。

- `core/` は、**ファイル形式に依存しない「変更の内容」**(追加・削除・変更した図形のID と、変更前後の図形)を作って返す。Undo も、この変更の内容を記録する。
- `io/` は、その「変更の内容」を受け取り、図形のID から元データの記録を引いて、差分(削除・差し替え・追加)に変換して適用する。
- 両者を呼び出して結びつけるのは、画面の側(将来は、画面と中核の間に置く「アプリの層」)。

## まだ整理していないもの(後の Phase で行う)

- 画面の側(`cad-view/`、`components/`)は、今の場所のままです。画面を作り直す Phase で、`render/`(描画)と `ui/`(React の部品)に分ける予定です。
- `core/model/convert.ts` は、範囲の計算を引数で受け取っています(Phase 1a で core の外にあったため)。Phase 1c で同じ `core/` に移ったので、直接呼ぶ形に簡単にできます(処理を変えないため、今はそのまま)。

## 開発用の入口(`src/devHooks.ts`)

`window.__cadDev` は、図面を編集するコマンドがまだ無い間に、「変更 → 表示 → Undo → Redo」をE2Eで確かめるための入口です。

- 開発サーバーのときだけ、`App.tsx` が動的に読み込みます(`import.meta.env.DEV`)。**本番ビルドには含まれません。** ビルドの成果物を検索して、含まれていないことを確認します(docs/regression-checklist.md)。
- 作図・編集のコマンド(Phase 4以降)ができたら、E2Eはそちらを使い、この入口は不要になれば削除します。
